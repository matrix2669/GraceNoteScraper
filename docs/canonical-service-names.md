# Canonical service name proposals

The builder may propose a descriptive name only from the audited exact-station
registry row's own name, subject to the active alias owner census, typed source
provenance, saved suppressions and global included-name collision checks. Existing
explicit provider rename rules take precedence. The default East annotation is
omitted only when it appears as a terminal source-row feed suffix; brands and
West/Pacific names are not stripped. Proposals are not decisions and do not by
themselves change a channel name or Lineuparr export.

A proposal must not be activated without a current consumer validation and the
associated fenced snapshot. Until validation exists or completes, the effective
pre-proposal names and existing decisions remain in use. Existing published
exports are not regenerated by proposing a name.

## Automatic admission and ordinary review

The existing coalesced background validation worker owns admission. Draft, review,
status and export reads do not start matcher processes. After a successful stream
refresh or durable choice, it captures the same safe inventory, source evidence,
configuration and decision revision. The first unchanged Exact95 consumer pass
compares the actual full exported lineup with all eligible name-only proposals.
Names that collide across **any** included category, including simultaneously
proposed names, are held before this pass. Alias pools are keyed globally by name;
category is not an identity boundary. Both raw descriptors and final East-stripped
values are checked against the actual saved suppression list.

Every newly matching physical stream must be covered by an existing target-scoped
literal-name Confirm. Deny wins, irrespective of its historical primary score.
Same-name replacement coverage follows the existing source/connection/target
contract, not fuzzy name normalization. Unresolved additions appear in the normal
stream review queue with their full raw names. Confirm and Deny remain the ordinary
controls; there is no separate name approval. A saved eligible confirmation, such
as an already confirmed WETV stream, does not require another confirmation.

For the admitted set, the worker reruns the **unchanged** threshold70 primary
matcher once against the captured safe streams and new names. It rebuilds all
automatic exclusions and supplemental projections, then checks the final full
JSON with the unchanged Exact95 consumer again. Losses, Deny conflicts or any
unapproved addition on any target hold the entire staged set. This is deliberately
bounded: at most two consumer passes and one primary pass per attempted input
revision, with a five-minute overall cancellation deadline. No iterative subset
search, per-name full-lineup loop, inventory fetch or matcher normalization change
is introduced. Primary Refresh takes priority and cancels background preparation.

Only after every check succeeds are the immutable name proof and newly scored
primary snapshot installed together under configuration, evidence, saved-state,
review and inventory fences. No durable choice, publication or downstream channel
is changed by this operation. Export admission additionally checks the name-proof
revision. Stale proofs cannot publish names; old-name fallback uses its retained
old-name scored snapshot, never relabeled scores. Failures and unresolved effects
are exposed through the existing validation status and ordinary review controls.
A failed check can be retried through the existing validation action; a restart
or changed inventory requires a new successful captured refresh and validation.

This changes names only when their actual consumer effects are safe for the
current captured inventory. Future inventory still requires validation. Existing
published JSON remains untouched until normal user-requested generation. A future
consumer sync may recreate name-keyed channels; it is not a reason to silently
retain an incorrect name, and this workflow neither deletes downstream channels
nor modifies the LineupARR plugin.
